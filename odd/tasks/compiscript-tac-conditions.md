# Compiscript conditional TAC
Objective: extend the verified numeric foundation with comparisons, booleans, short circuit and if/else, not the remaining Entrega 2 features.
Baseline `fbbb12b17d610c88770da12b9922431c529a488f`; integration `feat/compiscript-tac`; child `feat/compiscript-tac-conditions`; cached strategy `feature-branch-chain`; forecast 650–950 authored lines; runner offline `go test`.

## Specs

- **S1 — Authorized scope.** User: `siguele`, accepting: `La próxima unidad concreta sería comparaciones, cortocircuito e if/else, conservando las salidas numéricas existentes. Después seguimos con los ciclos.` Support `==`, `!=`, `<`, `<=`, `>`, `>=` for numeric operands; boolean equality/inequality, declarations, assignments and literals; unary `!`; `&&` and `||`; `if/else`, nesting and unbraced bodies accepted by the existing grammar. Strings, null, lists, objects, functions, assignment expressions, ternaries, loops, switch and transfers remain explicitly unsupported by TAC when not rejected earlier by analysis.
- **S2 — Control-flow semantics.** Preserve left-to-right evaluation. `&&` must skip its right operand when the left is false; `||` must skip it when the left is true. Generate deterministic labels, conditional and unconditional jumps; only the selected if/else body executes. Materialized logical expressions must initialize their boolean result on every path. Static analysis and lowering still validate unsupported/erroring source in branches that would be skipped at runtime. Do not constant-fold away validation or pretend unsupported syntax is supported.
- **S3 — Types, scopes and temporaries.** Numeric comparisons widen integer operands explicitly when needed, and comparisons/logical operations produce boolean operands. Preserve the semantic scope inventory and initializer-before-binding behavior in both branches. Never recycle a branch result or any value still needed through a recursive RHS or join. Continue using the existing temporary pool and read-before-write instruction semantics; instructions retain valid source spans. No changes to AST, semantics, grammar, generated sources, dependencies or generation scripts.
- **S4 — Atomic errors and compatibility.** No TAC or partial instruction stream escapes on parsing, semantic, or unsupported-lowering errors, including unsupported RHS/branch content. Existing supported numeric programs must retain exact TAC text, JSON, diagnostics and exit behavior against the baseline. Previously rejected booleans, comparisons, logical expressions and if/else intentionally gain support; update their tests and applicable type-support wording. Do not change existing analysis CLI/HTTP reports or command flags. Add control-flow metadata only as optional instruction fields so old numeric serialization stays identical.
- **S5 — Behavioral proof.** Observe RED before implementation and GREEN afterward through `Compile` and the real TAC CLI. Commit bounded reference-interpreter tests that execute labels/branches, read operands before writes, detect undefined temporaries/labels and division by zero, and bound execution steps. Prove skipped RHS traps and selected RHS execution, nested logical joins and if/else, else-if, no-else, shadowing, conversion, deterministic labels, live-temporary correctness, atomic rejection and unchanged inputs. Use independent scratch probes plus baseline stdout/stderr/exit comparisons; source-mutating full-suite tests run only in isolated external scratch.
- **S6 — Delivery.** Update the TAC design, help/usage documentation as applicable, and a runnable conditional `.cps` example; distinguish this subset from full Entrega 2. Preserve the original untracked Finder files/PDF. Reuse the selected integration chain, do not merge main or create PRs. Risk: item 3, because existing TAC instruction rendering and expression/lowering helpers are shared contracts whose numeric output must remain stable.
